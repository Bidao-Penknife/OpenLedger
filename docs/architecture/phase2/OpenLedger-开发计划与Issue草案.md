## 1. 工作约定

按“设计确认 → 小 Issue → 实现 → 验证 → 阶段汇报 → 等待下一步指令”执行。稳定性优先，未达到阶段验收时先修复，不以增加新功能掩盖缺陷。阶段 1 已交付；阶段 2 的设计包与 Schema 验证已完成，等待本阶段评审；阶段 3 尚未开始。

每个正式 Issue 采用：问题/目标、用户行为、实现范围、验收标准、验证方法、依赖、明确不做事项。每个 PR 写清行为变化与实际验证，不声称未运行的检查已通过。

阶段门禁通用要求：相关测试通过、资金不变量不破坏、错误路径可恢复、文档与功能状态一致、没有提交用户账本/密钥/真实个人财务样例。业务单元测试从有实现的阶段开始；设计阶段以评审与需求覆盖核对验收。

## 4. 示例 Issue 正文

### OLG-012：实现账户转账、期初余额与余额校准

**问题与目标**：转账应改变两侧账户余额，同时保持总资产与收支统计一致。用户需要记录初始资金和校准实际余额，并能追溯差额。

**范围**：同币种账户转账；账户创建时的非零期初交易；余额校准差额交易；事务、审计、幂等提交。

**验收标准**：

- 账户 A 初始 1000 元、B 初始 200 元；A 向 B 转账 300 元后，A=700、B=500，总资产=1200，收入/支出=0。
- 插入第一侧流水后注入失败，A/B/总资产仍保持操作前状态，没有半笔交易或成功回执。
- 同账户、跨币种、零/负转账金额被拒绝；输入金额精度超限被拒绝。
- 相同 request_id 重试不新增交易，返回一致结果。
- 对 A 校准到 650 元，差额 -50 元可追溯，支出统计不因此增加。
- 转账费用需要额外支出记录；首版不做自动手续费拆分与跨币结算。

**验证**：真实临时 SQLite 集成测试、资金领域单元测试、事务回滚测试。页面验收随 OLG-018 补齐。

### OLG-015：自然语言解析生成可确认草稿

**问题与目标**：用户希望输入口语描述获得记账草稿，避免大量表单输入，同时不会因推断错误直接修改余额。

**范围**：人民币金额、明确收入/支出词、相对日期/时段、常见分类与支付渠道；可注入参考时间；候选与证据。

**验收标准**：

- 参考日期 2026-10-02，示例原文解析出 12800 分、2026-10-01、晚上、支出、餐饮建议、微信渠道、朋友对象；商家/地点不凭空生成。
- “咖啡25元”可生成草稿，默认账户/日期标记为默认值；解析过程中数据库不发生写入。
- “昨天吃饭128，朋友转我50”标为多笔待确认，不取第一笔后丢弃后半句。
- 数字时刻与金额不会混淆；缺金额返回缺失字段提示；同一句在固定时钟下结果可重复。
- 无 AI 凭据或网络依然工作；AI 融合在 OLG-027 中单独实现。

**验证**：参数化规则用例、跨年/月底日期测试、歧义与缺失字段测试，失败样本加入合成回归语料。

## 5. 阶段汇报模板

每次阶段交付展示：

1. 已完成 Issue 与实际可用行为。
2. 关键目录与新增接口；重要设计决策及其理由。
3. 运行过的测试/检查命令和结果；手测范围与环境；没有运行的项目明确列出。
4. 已知问题、限制与尚未实现的功能。
5. 当前可审查的源码或制品路径，以及下一阶段的范围。

阶段末等待用户下一步指令，不以“CI 文件存在”代替 CI 已通过，也不以“打包脚本存在”代替 exe 已在干净 Windows 环境验证。
