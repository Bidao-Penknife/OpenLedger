## 2. 数据库实际检查

最终 DDL 实际创建 14 张用户表、27 个显式索引和 2 个查询视图；所有用户表均为 STRICT。验证已检查外键开启、整数金额及范围、分类种类匹配、日期字段形状与时间精度组合、有效来源枚举、重复标签和导入来源身份、回执 JSON、审计与回执的延迟外键、附件路径的基础约束。

使用完整样例资金事件验证了：

- 期初、收入、支出、转账、退款和校准对账户余额的贡献；无流水账户余额为零，归档账户仍计入资产。
- 两账户转账保持总资产不变；不同账本使用同一全局账户，而账本收支查询仍独立。
- 退款按原支出的账本与分类归集，修改原分类后退款查询随之变化；转账、期初和校准不计入收支。
- 软删除与恢复改变余额和统计的查询贡献；已软删除的导入记录仍占用严格来源身份。
- 在第一条转账流水写入后回滚，交易头与已写流水都不存在，未留下半笔转账。
- 审计引用尚未写入的命令回执可在同一事务最后补齐；提交时仍缺回执则拒绝。
- SQLite 整数 SUM 溢出有明确错误；验证脚本逐行 BigInt 累计能保留精度。正式产品的 Python int 回退路径仍待实现和测试。
- 最终临时数据库通过 `integrity_check` 和 `foreign_key_check`。

这些检查直接操作 SQLite 样例，证明的是 DDL 和视图行为。回滚演示不证明尚未存在的 `TransactionService` 已实现正确，也不证明并发、幂等重放或崩溃恢复已经通过产品级测试。

## 3. 必须由应用承担的约束

72 项检查中包含 5 项“责任边界探针”：它们特意展示数据库单独不能拒绝的情况，而不是将这些情况当作有效业务。

| 探针 | 实际观察 | 资金核心阶段必须实现 |
| --- | --- | --- |
| 只有交易头、没有账户流水 | 原始 SQL 可以插入 | 提交前校验各 kind 的完整流水条数、符号、金额 |
| 累计退款超过原支出 | 现有行级约束不能计算总额 | 写锁内读取活跃退款并验证本次变更后的额度 |
| 未来业务日期 | 静态 CHECK 不依赖今天 | 使用可注入 Clock 与用户时区拒绝未来事件 |
| 2 月 31 日等非法日历日期 | 日期形状检查允许 | Python date/日期解析器验证真实日历 |
| 交易日期早于账户起点 | 跨表日期比较未在 CHECK 表达 | 用例验证所有涉及账户的 `balance_start_on` |

因此，应用只能经统一写入用例操作资金聚合，不能把“SQL 约束检查通过”当作“账务有效”。备份恢复时同样需要资金不变量检查。资金核心阶段将增加退款并发、账户余额范围、期初唯一性、幂等与版本冲突的真实服务测试。

## 4. Python 运行环境兼容性

收尾时检测到的环境为 CPython 3.12.5 x64，自带 SQLite 3.45.3。补充检查确认该环境可以执行最终 DDL，创建全部表/索引/视图，支持 STRICT 和所用 JSON 函数，启用外键，并通过完整性检查；Python `Connection.backup()` 能复制已提交的样例数据库。

本组检查使用默认 rollback journal（`delete`），没有开启 WAL，也没有测试锁竞争或在线恢复。当前 Python 的 SQLite 版本不符合[阶段 1](OpenLedger-阶段1-需求与技术方案.md)中首选的 WAL 修复版本门槛。阶段 3 必须记录实际构建运行库，选择已验证版本或保留 rollback journal，并验证发行包；不能因为另一组 Node 验证用了 SQLite 3.51.3，就推断 Python 冻结程序也使用该版本。本阶段未安装、升级或锁定应用依赖。
