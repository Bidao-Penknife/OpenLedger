# ADR-011：SQLite 功能探测与保守 WAL 门槛

状态：阶段 3 已采用版本判断和启动探测；真实资金连接与日志模式在阶段 4 实施。日期：2026-10-02。

## 决策

启动使用临时内存连接探测 STRICT 表和所需 JSON 函数，随后关闭连接。阶段 3 不创建资金数据库，不改变用户数据库日志模式。运行环境显示 Python/Qt/PySide6/SQLite 的实际版本，不假设 PySide6 安装会升级 Python sqlite3。

SQLite 官方明确 WAL-reset 修复包含 3.51.3 及后续版本，并提供 3.44.6、3.50.7 分支回补。当前策略只接受已知正常的纯版本字符串：`>=3.51.3`，或 `3.44.6<=v<3.45.0`，或 `3.50.7<=v<3.51.0`。未知字符串保守拒绝 WAL；版本探测不替代未来并发与检查点测试。

本机 CPython 3.12.5 的 sqlite3 使用 SQLite 3.45.3，具备所需 DDL 能力，但不通过 WAL 门槛。阶段 4 默认使用 rollback journal（DELETE），在写队列、busy timeout 与真实锁竞争测试通过后工作；升级到符合门槛的运行库后再显式验证 WAL 路径。

不能把阶段 2 Node.js 里的 SQLite 3.51.3 结果用于证明 Python exe 使用了相同运行库。源码和冻结验证都记录实际 `sqlite3.sqlite_version`。

## 后果与验证

回滚日志下读写并发能力需要实际测试，界面不得长期占用读事务。应用默认本地磁盘，不对网络共享数据库作兼容承诺。已开启 WAL 的现有库若由不符合门槛的运行库打开，阶段 4 必须检查并拒绝危险写入或经受控维护转换，不能静默假设安全。

版本边界已有参数化测试；STRICT/JSON 的实际连接探测有测试。真正的持久连接、迁移、写 UoW 和日志模式切换尚未实现。

依据：[SQLite 官方 WAL 文档第 11 节](https://www.sqlite.org/wal.html)。
